# SPEC-03 & SPEC-04: Comment upsert and Action distribution — Design

Linear: [SCA-112](https://linear.app/scalingforge/issue/SCA-112/spec-03-publicacion-y-actualizacion-del-comentario-en-el-pr) (comment upsert), [SCA-113](https://linear.app/scalingforge/issue/SCA-113/spec-04-empaquetado-y-distribucion-como-github-action) (distribution)
Milestone: GitHub Action + Text Brief MVP (M0)

# SPEC-03: Publishing and updating the PR comment

## Purpose

Keep a single, identifiable comment per PR up to date with the latest brief
from `pr-trailer-api`, instead of posting a new comment on every run. A
reviewer opening a PR after several pushes should see one comment reflecting
the latest state, not a growing thread of duplicates.

## Out of scope

The exact markdown content of the brief (risk table, reading-order list) —
that's generated by `pr-trailer-api` (SPEC-02, a separate repo, not yet
implemented). This spec only wraps whatever `message` string it receives with
a hidden marker and a footer signature, and decides whether to create or
edit a comment. No parsing or validation of the brief's markdown.

## Architecture

A new module, `src/github/upsert-comment.ts`, exports:

```ts
export const PR_TRAILER_MARKER = '<!-- pr-trailer:v1 -->';

export async function upsertPrComment(
  octokit: Octokit,
  params: { owner: string; repo: string; pullNumber: number },
  body: string,
): Promise<void>;
```

The final comment body is composed as:

```
<!-- pr-trailer:v1 -->

{body}

---
🤖 *Posted by [pr-trailer](https://github.com/yasel-scf/pr-trailer-ghaction)*
```

The marker sits on its own line at the very top (hidden — HTML comments
don't render on GitHub), so it's never truncated if GitHub ever clips a very
long comment. The footer signature is a fixed string identifying the Action
as the source, independent of whatever `pr-trailer-api` returns.

## Data flow

1. `upsertPrComment` lists every comment on the PR via
   `octokit.paginate(octokit.rest.issues.listComments, { owner, repo, issue_number: pullNumber, per_page: 100 })`.
2. Finds the first comment whose `body` includes `PR_TRAILER_MARKER`.
   Comments from other users/bots that don't contain the marker are ignored.
3. If found: `octokit.rest.issues.updateComment({ owner, repo, comment_id, body: composedBody })`.
4. If not found: `octokit.rest.issues.createComment({ owner, repo, issue_number: pullNumber, body: composedBody })`.
5. `src/index.ts` replaces its current direct `octokit.rest.issues.createComment(...)`
   call with `upsertPrComment(octokit, { owner, repo, pullNumber: pullRequest.number }, message)`.
   Everything else in `index.ts` (fetching the brief from `pr-trailer-api`,
   error handling) is unchanged.

## Testing

- `upsertPrComment` takes an octokit-shaped fake, same pattern as SPEC-01's
  `extractPrContext` tests: `{ paginate: vi.fn(), rest: { issues: { listComments, createComment, updateComment } } }`.
- Test cases:
  - No existing comment with the marker → calls `createComment`, never `updateComment`.
  - An existing comment with the marker → calls `updateComment` with its
    `comment_id`, never `createComment`.
  - Other comments without the marker (from other users/bots) are present →
    ignored, don't get mistaken for the tracked comment.
  - Composed body contains marker, then the passed-in content, then the
    footer signature, in that order.

# SPEC-04: Packaging and distribution as a GitHub Action

## Purpose

Let any team install `pr-trailer` in their repo in under 5 minutes by
following only the README — no code changes in the consumer repo, just a
workflow YAML file.

## Out of scope

Build tooling (resolved in SPEC-00). Per-client API key issuance /
multi-tenant key management — the current `pr-trailer-api` backend still
uses a single fixed key (see
`docs/superpowers/specs/2026-07-04-action-api-wiring-design.md`); the README
describes the request flow in self-serve product language regardless, with a
placeholder URL until a real signup destination exists.

## `action.yml`

Already satisfies the AC as-is (no code change needed): `api-key` (required,
no default) and `github-token` (optional, defaults to `${{ github.token }}`).
This spec only adds the README that documents them — it does not add
`exclude-files` or any other SPEC-01 input, since those aren't implemented
in this repo's `action.yml` yet.

## README.md

New file at the repo root, written in English (public-facing communication
is English-only per project convention). Sections:

1. **Title + one-line description** of what the Action does.
2. **Quickstart workflow** — a complete, copy-pasteable YAML block based on
   the existing `.github/workflows/pr-trailer.yml`, using
   `uses: yasel-scf/pr-trailer-ghaction@<version>` with `api-key` and
   `github-token` wired up.
3. **Getting an API key** — self-serve instruction with a placeholder URL:
   `Request an API key at https://TODO-replace-with-pr-trailer-signup-url`,
   then add it as a repo secret (e.g. `PR_TRAILER_API_KEY`) referenced from
   the workflow.
4. **Inputs table** — `api-key` (required) and `github-token` (optional,
   default `${{ github.token }}`), matching `action.yml` exactly.
5. **Example output** — an illustrative sample comment showing a risk table,
   a reading-order list, and the SPEC-03 marker/footer, explicitly labeled
   as illustrative (e.g. "illustrative — final format lands as SPEC-02
   completes") since the real content generation isn't implemented yet.

No separate `docs/` page — two inputs and one workflow example don't warrant
splitting instructions across files, and a single README serves the
"under 5 minutes, no prior context" goal directly.

## Testing

Documentation only — no automated test. Manual acceptance: the Quickstart
YAML block, copy-pasted into a fresh repo with a valid `api-key` secret,
runs successfully with no other changes.

# Decisions log

| Decision | Choice | Rationale |
|---|---|---|
| Locating the previous comment | Scan via `listComments` + marker | Actions have no persistent state between runs; scanning is robust to any runner/cache changes |
| Marker placement | Start of the comment body | Common bot convention; never clipped if GitHub ever truncates a long comment |
| Footer signature | Fixed text with a link to the Action's own repo | Identifies the source independent of whatever dynamic content the brief contains |
| README — API key section | Placeholder URL, self-serve tone | Public copy is forward-looking product language; doesn't expose that today's backend uses one shared key |
| README — output example | Illustrative, explicitly labeled as such | AC asks for "expected output"; the real thing depends on SPEC-02, which lives in a different repo and isn't built yet |
| Docs structure | Single root README, no extra `docs/` page | Two inputs don't justify more structure; keeps setup time under 5 minutes |
| `action.yml` inputs | No change | Already matches the AC (`api-key` required, `github-token` optional) from the prior wiring spec |
